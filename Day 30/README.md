## 🔐 Pydantic Validation

The `/predict` endpoint uses a strict Pydantic request model.

The request validates:

* `Age`
* `Gender`
* `Product_Category`
* `Quantity`
* `Price_per_Unit`

Additional fields are rejected, while invalid field values are handled through Pydantic validation.

Invalid schema-level requests return:

```text
422 Unprocessable Entity
```

This prevents malformed or structurally invalid data from reaching the ML inference pipeline.

---

## 📊 OOD Guardrails

The service performs statistical Out-of-Distribution detection using IQR-based boundaries.

The tested boundaries were calculated from the retail sales dataset:

| Feature        | Lower Boundary | Upper Boundary |
| -------------- | -------------: | -------------: |
| Age            |          -7.00 |          89.00 |
| Quantity       |          -3.50 |           8.50 |
| Price per Unit |        -375.00 |         705.00 |

A value can satisfy Pydantic's schema constraints while still being statistically out-of-distribution.

For example:

```text
Price_per_Unit = 800.0
```

passes the basic Pydantic maximum of `100000`, but exceeds the statistical OOD upper boundary of `705`, resulting in:

```text
400 Bad Request
```

This provides an additional layer of protection before model inference.

## 🧪 Automated Integration Testing

Integration tests were implemented in:

```text
test_integration.py
```

The test suite verifies four important API behaviors.

### 1. Valid Prediction

A valid request must return:

```text
200 OK
```

and contain a structured:

```json
{
  "prediction": "0"
}
```

or another valid model prediction.

### 2. Invalid Input

Invalid Pydantic values must return:

```text
422 Unprocessable Entity
```

### 3. Out-of-Bounds Input

Statistically out-of-distribution values must return:

```text
400 Bad Request
```

### 4. Malformed Request

Malformed JSON must not cause a server crash or:

```text
500 Internal Server Error
```

## 📈 Testing Strategy & Observations

The testing strategy was designed around multiple layers of API reliability:

### Layer 1 — Schema Validation

Pydantic validates the structure and basic constraints of incoming requests.

### Layer 2 — OOD Detection

Statistical IQR boundaries detect values that are outside the expected data distribution.

### Layer 3 — ML Inference

Only validated and accepted requests proceed to model inference.

### Layer 4 — Integration Testing

Pytest verifies the complete API behavior for valid, invalid, OOD, and malformed requests.

### Layer 5 — Container Verification

Docker verifies that the complete service can start successfully and serve real HTTP requests.

### Layer 6 — Backend Integration

The backend client verifies that another application can communicate with the ML service and consume its structured response.

---

## 🧠 Key Engineering Observations

### Pydantic improves API reliability

Strict validation prevents invalid data from entering the ML pipeline and provides clear `422` responses for schema violations.

### OOD guardrails provide an additional safety layer

Pydantic checks whether values satisfy the API schema, while statistical OOD detection checks whether numerical values remain within the expected data distribution.

### Docker improves deployment consistency

Containerization packages the FastAPI application, dependencies, model, feature configuration, and dataset into a reproducible runtime environment.

### Integration testing catches cross-component failures

Automated tests verify that the API behaves correctly beyond individual functions, including validation, error handling, and prediction workflows.

### Structured responses simplify backend integration

The backend receives a predictable JSON response containing the model prediction, making the ML service easier to consume from another application.
